⏺ Locked. Now the question that's been hanging implicitly: when the share sheet 
  hands you a URL or text blob, what do you turn it into? Because "a saved spot"
   needs to be act-on-able later — at minimum, a name and a location. Otherwise
  retrieval is broken even with one category.

  My recommendation: Apple MapKit / MKLocalSearch lookup, on-device, no backend 
  in v1. The flow: share sheet receives URL/text → simple extraction (regex on
  common patterns: Apple Maps URLs encode the place directly; Google Maps URLs
  have coords/place IDs; for plain text or article URLs, grab the title + try to
   pull a place name) → query MKLocalSearch → store the resolved place (name,
  address, coords, category) + the original URL as a "source."

  Reasoning: MapKit is free, key-less, on-device, no backend required, no auth
  required. Quality is "good enough" for major foodie locations in big cities —
  which is where your users will mostly be. Google Places is better data but
  requires a backend to hide the API key (you cannot ship an unproxied Google
  API key in a client; it'll get scraped within hours). LLM-based extraction is
  even better but adds cost + a server. Both are reasonable v2 upgrades when
  you've validated the bet.

  The risk in this pick: international / very-long-tail spots may not resolve
  cleanly via MapKit. Acceptable v1 fallback: if no MapKit match, save the raw
  URL + title as a "rough" spot the user can manually fix later.

  Now I want to ask a question that gets asked too late in most MVPs: what is 
  the success criterion? Because "ship the MVP and see what happens" is a
  guarantee of building v2 on vibes. You should commit to a falsifiable
  threshold before you start, so you don't move the goalposts when the numbers
  come in.

  My recommendation: dual criterion, qualitative + light quant, time-boxed at 4 
  weeks of TestFlight use.

  - (a) Founder dogfood test: You save ≥3 spots/week for 4 consecutive weeks
  without forcing yourself. If you don't, the friction bet failed for the person
   who cares most. Kill it.
  - (b) Peer signal: ≥3 of your ~10 TestFlight friends save ≥1 spot in week 2
  (i.e., return to it without you nudging them). Doesn't have to be a lot — it
  has to be unprompted.
  - (c) Loop-closing signal: ≥25% of all saved spots across all users get
  marked-visited within 30 days. Tests whether saving translates to going.

  If all three pass: it's working, build v2 (which probably means categories,
  then social). If (a) fails: kill or pivot — the founder isn't using it. If (a)
   passes but (b) fails: it's a personal utility, not a product — fine outcome,
  but don't keep building social. If (a) + (b) pass but (c) fails: people are
  hoarding bookmarks, not visiting — the value hypothesis is broken even if
  capture isn't.

  At ~10 users, the numbers are noisy by definition — these are read as
  "directional yes/no," not statistical confidence intervals.
